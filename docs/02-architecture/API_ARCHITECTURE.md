# WorkOS API Architecture

## Versioning

New productized contracts are introduced under `/api/v1`. Existing imported routes may remain temporarily behind compatibility adapters while behavior is migrated and tested.

The WOS-03 API foundation begins with an incremental pilot: identity reads (`/api/auth/me` and `/api/auth/organization-scopes`), organization setup, and scoped audit, import, and integration-event history (`/api/audit-logs`, `/api/import-export-logs`, `/api/integrations/events`, and their `/api/v1/...` aliases) are mounted through shared handlers. It also has separate deployment and organization audit reads at `/api/deployment-audit-logs` and `/api/organization-audit-logs` with matching `/api/v1/...` aliases. Deployment history contains only rows whose organization and legal-entity scopes are both null. Organization history contains only rows owned by the explicitly selected organization whose legal-entity scope is null. Each reader requires its protected permission, an active account, an active role still assigned to the account, and an explicit per-user grant; organization grants are specific to each organization. The existing `permissions.manage` authority can manage those designations, while role-wide and generic organization-audit grants are rejected. No auditor access is granted by default. Both readers reuse audit-history redaction and leave the exact-pair filters on ordinary scoped history unchanged. A `/api/v1` route must preserve legacy authorization and business rules while returning the versioned error contract below. New routes should be added under `/api/v1`; legacy paths remain until an explicit deprecation plan removes them. This pilot does not claim that every existing API route has already been migrated.

The generic import/export-history writer now shares the same imports capability router at `POST /api/import-export-logs` and `POST /api/v1/import-export-logs`. Both require `imports.manage`; history remains exact-pair scoped and may expose saved filenames, row-error details and caller-supplied source identifiers to authorized import users, validate the same legacy payload, and persist the authenticated username and server-resolved organization/legal-entity pair. Success remains HTTP 200 with the returned row array. Legacy validation/database errors retain their existing bodies; v1 errors use the stable envelope below. Free-form channel labels, optional diagnostic source identifiers and omitted-versus-empty errors retain their legacy meaning. This extraction adds no import execution, idempotency, grants, schema, retention or broader audit policy.

The import/export page presents authorized history through a read-only detail panel: eight operations per page across the existing latest-100 response, batch reference/channel/result, schema version and server-side dry-run state when present, and saved row diagnostics with optional source identifiers. Diagnostics render as escaped text and expand in groups of twenty. Empty/loading/failure states are distinct; retry does not mutate history. Refresh, unmount and organization-scope changes invalidate older responses and clear prior detail state. Pending import rows and asynchronous dry-run/apply requests are bound to the captured organization/legal-entity pair; scope changes discard pending rows, block a request if scope changes during backend detection, and hide a late apply result while directing the user to check history in the original scope. Export reads also capture their initiating scope and are canceled before download if it changes; export and generic import-history writes use that same scope for history and audit requests. The existing `imports.manage` permission gates import-history reads, so users with that permission but without `employees.manage` may see saved filenames, row-error details and source identifiers only for their exact selected organization/legal-entity pair. No permission or role is created, no broader scope is granted, and export/retention policy is unchanged.

Project Master CSV apply is also mounted through one shared handler at `POST /api/imports/projects/apply` and `POST /api/v1/imports/projects/apply`. In backend mode, the Import / Export UI now performs the versioned server dry run before apply and offers only server-approved rows. A newly selected file receives separate dry-run and apply idempotency keys; an identical request retry keeps its original key and payload, while reselecting a changed file starts a new operation with new keys. The legacy endpoint keeps its existing payload, `imports.manage` gate, organization/legal-entity checks, partial-result semantics and response shape. The versioned contract requires `schemaVersion: "project-master/1"` and an `Idempotency-Key`; it serializes retries per server-resolved organization, legal entity, authenticated actor, channel and key, replays the original batch for an identical canonical request, and returns a stable conflict for a changed request. A provided v1 `clientId` is authoritative and is looked up only in the selected scope; it is not combined with a potentially conflicting display-name match. Project-code writes from both import paths and the normal `POST /api/projects` writer acquire organization-scoped advisory locks in sorted order before reading prior values. This serializes cross-route writes so import audits retain the correct create/update state. If a saved project changes between the initial lookup and lock acquisition, the normal writer returns a stable conflict rather than using a stale prior value. `dryRun: true` validates references and duplicates, records a batch plus audit evidence, and does not mutate projects or emit project-row audits. For the versioned endpoint only, blank optional status cells are treated as omitted so the existing default applies; nonblank invalid statuses remain rejected. The legacy schema retains strict blank-status validation. Versioned dry runs allow zero valid rows so fully rejected uploads can still be recorded; legacy requests and versioned applies still require at least one row. Versioned cross-scope project-code conflicts use a generic unavailable-in-scope message; the legacy response remains unchanged. Migration `039_wos03_import_operation_contract.sql` adds nullable schema-version metadata, a default-false dry-run flag and scoped idempotency records linked to their import batch; deleting a batch cascades to its key record, so no separate key-retention window is introduced. Import-history reads use the existing `imports.manage` gate within the exact selected pair; this does not change the existing batch-retention policy. Employee Master server dry-run and full WOS-03B acceptance remain open.

Employee Master has shared apply handlers at `POST /api/imports/employees/apply` and `POST /api/v1/imports/employees/apply`. The versioned contract requires `schemaVersion: "employee-master/1"` and `Idempotency-Key`, with serialization by server-resolved organization, legal entity, authenticated actor, operation channel and key. Its durable canonical request hash excludes `initialPassword`: a same-key retry that changes only that field replays the first committed result and does not change credentials; changing any other canonical field returns `IDEMPOTENCY_KEY_REUSED`. The v1 response marks first acceptance with `replayed: false` and a returned stored result with `replayed: true`; the browser identifies that replay and says it did not change credentials. Apply identity excludes filename and free-form client diagnostic text, retaining schema version, total row count, original row numbers, allowlisted field names and non-credential row data. Versioned apply batches use the server-controlled label `Employee Master import.csv`, and client preflight errors use server-controlled messages; submitted credentials echoed in validated source identifiers are redacted. The legacy alias retains its existing filename/diagnostic behavior with exact submitted-credential echo redaction, and the browser also sanitizes local preflight filenames and diagnostics. Password resets remain in the existing protected reset flow, and no credential-derived fingerprint is stored in idempotency evidence.

Employee Master server validation is available with `dryRun: true` on the versioned handler. It requires the same fixed safe filename, rejects any request containing an `initialPassword` property, and accepts only a non-secret `initialPasswordPresent` boolean on preview rows to indicate whether the client has a password value available for a later apply. That indicator is request data, not proof or credential validation; apply still requires the actual value under its existing behavior. Dry-run validation checks selected-scope references, conflicts, reporting relationships and lifecycle rules. It simulates accepted earlier row manager changes in memory, so later rows are checked against the same source-order graph used by apply while no relationship is written. It records a server-labeled `dry_run=true` batch, an ImportBatch audit and a scoped idempotency result in a separate `Employee Master Dry Run` channel; it does not write employee, account, role, data-scope, worker-profile/history or credential records, or employee-row audits. Saved and returned preview diagnostics contain only row number, allowlisted field/code and server-controlled safe text; they omit client messages, source identifiers and filename values. Preview request hashes exclude client messages/source identifiers and any credential field while retaining non-secret employee-row data and the presence indicator. Same-key retries replay the original preview; changed canonical non-secret data conflicts. In backend mode the UI performs this preview before enabling Employee apply, sends no password in the preview request, and uses separate stable preview/apply keys; a failed preview can be retried with its original request/key. Existing apply authorization, role/provisioning and exact-scope behavior is unchanged, and the legacy route does not enable server dry-run. Disposable PostgreSQL/API and browser contracts cover preview no-write behavior, metadata/audit/idempotency, same-key replay and changed-key conflict, safe diagnostics, scope and missing-password validation, plus separate preview/apply transport. Employee dry-run is implemented for this contract; full WOS-03B acceptance remains open.

Client Master CSV apply now uses the same versioned-operation table and evidence shape at `POST /api/v1/imports/clients/apply`; the legacy `/api/imports/clients/apply` route retains its existing payload, permission, scope checks, partial outcomes and response behavior. The versioned contract requires `schemaVersion: "client-master/1"` plus an `Idempotency-Key`, scopes retries to server-resolved organization, legal entity, actor and channel, replays an identical request, and conflicts when a key is reused with changed canonical input. For the versioned endpoint only, blank optional Client Master IDs and statuses are treated as omitted so server-generated IDs and existing defaults continue to work; nonblank invalid statuses remain rejected. The legacy schema and response shape remain unchanged. A server dry run validates client references and same-scope/cross-scope conflicts, records a batch and audit result, and does not create/update clients, director mappings, project associations, or client-row audits. The Import / Export UI uses separate dry-run and apply keys, retries the same validation payload after a temporary error, starts fresh keys for a newly selected file, and only enables apply after server confirmation.

Allocation Control and Timesheet Import now share a capability router mounted at both `/api/imports/...` and `/api/v1/imports/...`. The versioned contracts use `schemaVersion: "allocation-control/1"` and `schemaVersion: "timesheet-import/1"`, plus an `Idempotency-Key` scoped to the server-resolved organization, legal entity, authenticated actor and channel. Exact retries replay the original batch; changed canonical input conflicts. Dry runs validate existing reference, scope, period and policy rules, persist only the import batch, ImportBatch audit and idempotency evidence, and skip allocation/timesheet rows, entries and successful row/group audits. Versioned Allocation Control rejects duplicate natural keys after resolving employee and project aliases to canonical IDs, plus repeated supplied IDs; legacy Allocation Control keeps its prior repeated-ID rule. Its dry run simulates accepted earlier rows across both the source and destination employees when evaluating cumulative over-allocation without writing them. Timesheet Import resolves employee and project aliases before enforcing its duplicate natural key, applies the existing seven-day week-ending date rule to versioned requests, and continues to have no upstream row identifier, so both preflight and server errors/audits retain null source IDs; idempotency applies to the operation/batch, while a distinct key remains a new import that upserts one employee/week and replaces that group's entries. The legacy import contract remains unchanged. The Import / Export UI now performs server validation before either channel can apply, uses separate validation/apply keys, reuses the same payload/key for retries and starts fresh keys for a reselected file. Legacy payloads, `imports.manage`, selected-scope resolution, partial-result counts, allocation upserts, reporting-period checks, timesheet grouping/replacement and row provenance remain unchanged. History reads now use `imports.manage` within the exact selected organization/legal-entity pair, as approved by the product owner; no broader scope is granted. Employee Master and full WOS-03B acceptance remain open.

## Module boundaries

The server remains a modular monolith. New seams belong under `server/modules/<capability>/` for domain/application behavior and under `server/api/` for transport concerns. A module may depend on shared domain services and injected infrastructure, but should not import the Express application entry point or register routes as a side effect. Route registration stays explicit in `server/index.mjs` or a capability router factory; compatibility prefixes mount the same router/handler so they cannot drift. Transport middleware validates and translates requests, while authorization, organization scope and business rules remain server-owned.

The initial identity-access and audit modules extract reusable seams from the existing application entry point. Further extraction is incremental and tied to a concrete boundary; it does not authorize a broad rewrite or service split. The existing notification feed, read, template, preference, delivery-attempt and test-delivery handlers are likewise grouped in `server/modules/notifications/notification-router.mjs` with database, scope, audit and delivery dependencies injected from `server/index.mjs`. This is a route-boundary extraction only: legacy `/api` paths, current `notifications.view`/`notifications.manage` gates, active-role row scope, transaction and audit behavior, and the absence of notification `/api/v1` aliases remain unchanged. The existing leave type, policy, holiday-calendar, balance and request handlers are grouped in `server/modules/leave/leave-router.mjs` and receive the database, identity guards, scope resolver, leave helpers, approval operations and audit writer through the router factory. This is also a route-boundary extraction only: the legacy `/api/leave/...` and `/api/holiday-calendars` paths, permission gates, request validation and transition rules, transaction/audit behavior, and absence of `/api/v1` aliases remain unchanged. The existing availability report is separately mounted at legacy `/api/reports/availability` through `server/modules/reports/availability-report-router.mjs`, with the shared query runner, database/identity/permission guards and employee-scope resolver injected. Its `leave.self_service` gate, guard order, current server-local year, exact organization/legal-entity and active-role filtering, Approved leave/start-year and Active country/Global holiday rules, fixed annual formula, numeric response values and legacy failure response remain unchanged. No `/api/v1` alias, mutation, audit event, schema or reporting policy is added. Focused HTTP tests cover the route and injected dependencies; disposable PostgreSQL/API probes cover Employee, TeamLead, ProjectManager, CountryDirector and selected-pair Admin reads, unauthenticated/wrong-scope refusal and no read-side mutation audit. This bounded seam does not complete the broader reporting or WOS-03B acceptance requirements.

## Contract principles

- Request, query and response schemas are explicit and validated.
- Errors contain stable machine code, user-safe message and correlation ID.
- Lists are paginated and filterable for production-scale use.
- High-risk mutations use optimistic concurrency/version checks.
- Imports, finalization and adapter operations use idempotency keys where applicable.
- Cost and margin fields are absent from broad operational DTOs unless separately authorized.

## Request enforcement

```text
authenticated identity
→ active role
→ effective permission
→ organization/legal-entity boundary
→ entity relationship / row scope
→ business policy and current state
→ command execution and audit
```

Authorization runs before data is returned or mutated. UI state and request-supplied ownership fields are not trusted.

Employee-owned leave-balance writes resolve and lock the submitted employee through the server-verified organization/legal-entity scope and active-role data scope before loading an existing balance or applying an upsert. The resolved employee row supplies the ID used for the write, balance refresh, and audit ownership. A target outside that scope receives the same generic response as a missing target, without balance values, a mutation, or an audit row. A supplied balance ID is an update selector for a row matching that employee, leave type, and year; unknown and out-of-scope IDs receive the same generic not-found response. Without an ID, the route creates or upserts by employee, leave type, and year, and a new row receives a server-generated ID.

Deployment audit history is a narrow read-only exception to organization/legal-entity scoping, not a cross-scope bypass. The server authenticates the named identity without resolving a selected organization, then verifies the account is active, the token's active role remains assigned, and the user has both effective permission and the explicit `user_permission_grants` row for `audit.deployment.view`. The permission is protected, all role defaults are false, and role-wide enablement is rejected. The existing `permissions.manage` path can grant it to a different active user of any role, and that grant/revoke is recorded as a deployment-level null-scope audit event. The query returns only rows with both scope columns null and passes them through the same redaction used by scoped audit history. The existing `/api/audit-logs` query remains exact-pair scoped for every role.

Organization-owned audit history is a separate read-only view that returns only rows for the explicitly requested organization with `legal_entity_id IS NULL`. Organization profile and terminology mutations use this organization-only scope even when the writer selected one legal entity; the audit writer does not infer organization ownership from request scope. Migration `038_wos03_organization_audit_access.sql` permits the organization/null pair while retaining the existing organization/legal-entity composite constraint and all prior rows. A reader must have an active account, an active assigned role, the protected `audit.organization.view` permission derived from an explicit `organization_audit_grants` row, and a matching designation revalidated in the final data query. This route does not require a selected legal entity and excludes deployment/null-scope, legal-entity and other-organization records. `permissions.manage` can designate a different active user with active membership in the selected organization; the manager's active role, permission and selected scope are checked again in the grant/revoke transaction. Organization grants cannot be role-wide or assigned through the generic user-grant route, and the migration creates no live designations. Grant/revoke events are appended at the affected organization scope. Ordinary `/api/audit-logs` remains restricted to the exact selected organization/legal-entity pair.

## Commands and queries

Commands change state and must enforce validation, policy, concurrency and audit. Queries return scoped read models optimized for workspaces and reports. Long-running imports, exports, notifications or snapshots return operation/batch status rather than holding an unsafe request open.

## State transitions

Work period, approval, contract, project, commercial snapshot, billing-eligibility event, approved-unbilled item and invoice-ready batch transitions use explicit state machines. Invalid or stale transitions return deterministic conflict errors.

## Financial endpoints

Financial calculation APIs accept references to authoritative records, not arbitrary client-calculated amounts. Responses identify calculation version and snapshot IDs. Preview endpoints are clearly non-final and cannot be used to bypass approval, billing eligibility or finalization.

A calculation snapshot remains valuation evidence. It cannot be submitted directly as an invoice-ready line.

## Billing eligibility and invoice readiness endpoints

The server exposes distinct commands and queries for:

1. Evaluating an authoritative source version against source-specific approval, contractual-due, acceptance and commercial policy.
2. Creating a versioned `billing_eligibility_event` from exactly one supported source version.
3. Creating or querying the corresponding one-to-one `approved_unbilled_item`.
4. Transactionally acquiring current occupancy and creating exactly one current invoice-ready line/membership for that approved-unbilled-item version.
5. Reviewing, approving, cancelling before export, exporting, confirming billing and creating reversal/superseding correction evidence.

A batch-line command accepts only a server-resolved `approvedUnbilledItemId` and immutable item version plus allowed presentation metadata. It must reject requests that try to supply a raw work-entry ID, calculation-snapshot ID, milestone ID, fixed-fee schedule ID, retainer/managed-service event ID, adjustment ID, client-calculated amount, currency, organization or approval status as the direct batch source.

WorkOS v1 does not split one approved-unbilled-item version across multiple invoice-ready lines. The command inserts the immutable line/membership and the database-unique current-occupancy record for `(approvedUnbilledItemId, approvedUnbilledItemVersion)` in one transaction. A separately billable portion requires its own upstream authorized/versioned eligibility event and approved-unbilled item with reconciled totals.

Every accepted command revalidates:

- Active identity, role, permission and organization/legal-entity scope.
- The approved-unbilled item's current version and eligibility-event lineage.
- Source-specific approval or contractual-due/acceptance evidence.
- Eligible date, currency, amount, calculation/policy and rounding evidence.
- Reversal/supersession state.
- Absence of any existing database current-occupancy record for the same item ID/version, whether in the requested batch or another batch.
- Optimistic concurrency and idempotency key.

The current-occupancy database uniqueness constraint is authoritative under concurrent requests; a pre-check or parent-batch-state query is not sufficient on its own.

### Batch-line idempotency and duplicate behavior

- The first valid request creates one line/membership and acquires one current-occupancy record atomically.
- An identical retry using the same idempotency key and canonical request identity returns the existing line/membership and does not create another record.
- Reusing that key with different input is rejected.
- A different idempotency key or concurrent request for the same approved-unbilled-item version while occupancy exists returns a stable conflict, including when the requested batch is the same batch.
- A compatibility or bulk endpoint cannot bypass this behavior; each selected item independently acquires occupancy or returns its own conflict.

## Invoice-ready batch state contract

Canonical states are `Draft`, `Under Review`, `Approved`, `Exported`, `Billed/Confirmed` and `Cancelled`.

The API and database use these exact occupancy classes:

- **Open/active occupying:** `Draft`, `Under Review`, `Approved`.
- **Final occupying:** `Exported`, `Billed/Confirmed`.
- **Non-occupying terminal:** `Cancelled`, only when cancelled before a successful export or billing confirmation.

Minimum accepted transitions are:

```text
Draft → Under Review | Cancelled
Under Review → Draft | Approved | Cancelled
Approved → Exported | Cancelled
Exported → Billed/Confirmed
```

`Cancelled` and `Billed/Confirmed` are terminal. `Exported` cannot transition to `Cancelled`. Export/billing corrections create versioned reversal or superseding billing-eligibility events, approved-unbilled items and correction batch lines rather than releasing or reusing the original lineage.

A failed export or artifact-generation attempt leaves the batch in `Approved`, keeps its current-occupancy records and register items occupied and records a failed operation. The state becomes `Exported` only through one of these accepted paths:

1. A configured finance provider accepts the exact immutable versioned payload and matching control totals.
2. WorkOS atomically creates and records an immutable versioned CSV export artifact, validates its control totals, and makes that exact artifact available for controlled retrieval.

A CSV acceptance record contains export-operation ID, idempotency key, immutable artifact ID/version, checksum, schema version, line count, control totals, generated timestamp and authorized actor. Repeating the same idempotency key returns the same accepted artifact and operation result; it does not regenerate content or reapply `Approved → Exported`. Corrected content requires versioned reversal/supersession lineage and a new correction batch or export artifact.

An initial delivery/export command is accepted only for an `Approved` batch. `Exported` and `Billed/Confirmed` batches may expose idempotent retrieval/redownload of their already accepted artifact and status confirmation, but they cannot initiate a second downstream delivery or transition to `Exported` again.

A cancellation command is accepted only from `Draft`, `Under Review` or pre-export `Approved`, requires reason and applicable approval authority, and atomically records cancellation plus deletion/release of each current-occupancy record. It returns an item to the available approved-unbilled register only when the underlying eligibility event remains current, unreversed, unsuperseded, in scope and otherwise eligible. Historical line/membership evidence remains immutable. Re-batching creates a new line/membership version and reacquires current occupancy; it never reactivates or rewrites the cancelled line.

`Exported` and `Billed/Confirmed` occupancy is permanent. There is no API command to release it.

The API returns stable conflict codes for:

- Direct-source/snapshot bypass.
- Stale event/register/batch version.
- Current line already exists for the approved-unbilled-item version in the same batch.
- Current occupancy already belongs to another open/active or final batch.
- Concurrent duplicate occupancy acquisition.
- Partial-billing or presentation-splitting attempt using the same approved-unbilled-item version.
- Initial export from any state other than `Approved`.
- Duplicate downstream delivery from `Exported` or `Billed/Confirmed`.
- Cancellation after export or billing confirmation.
- Reversed/superseded source or register item.
- Invalid transition.
- Invalid batch scope/currency.
- Control-total mismatch.
- Idempotency-key reuse with a different line, payload or artifact version.

Invoice-ready lines expose traceability to exactly one approved-unbilled item and through it exactly one billing-eligibility-event version. Raw source evidence may be included as read-only lineage; it is never accepted as an alternative batchable object.

## Integration and notification contracts

Inbound adapters map external identifiers to controlled domain records and retain source/idempotency evidence. Initial outbound finance delivery originates only from an `Approved` batch. Provider acceptance or atomic CSV-artifact acceptance performs the single `Approved → Exported` transition. Final-state endpoints support only idempotent retrieval/redownload and status confirmation of the already accepted artifact.

Notification commands create scoped notification records and delivery attempts separately from the core transaction. Requests resolve recipient scope, template version, preferences, channel eligibility and sanitized payload server-side. Provider retries use idempotency keys and cannot create duplicate in-app, email or collaboration delivery evidence.

## Observability

Every API request receives a correlation ID. A caller-provided `X-Correlation-ID` is accepted only when it matches the bounded safe-character format; otherwise the server generates one. State-changing HTTP methods also receive a server-generated operation ID. The Entra OAuth callback is a protocol-compatible GET with side effects, so that callback generates its own server operation ID without changing the read-only GET policy for other routes. Both IDs are returned as response headers and are exposed through CORS for browser clients. These identifiers are tracing aids, not authentication, idempotency or authorization tokens.

Failures served under `/api/v1` use `{ "error": { "code", "message", "correlationId", "operationId?" } }`. Codes are stable uppercase identifiers, messages are user-safe, and unexpected 5xx details are not returned. Legacy paths preserve their existing response shapes during the adapter period. The frontend error type retains HTTP status and available trace IDs for support diagnostics. Import preview/apply and history-load failures now present optional correlation/operation references beside their existing fixed corrective guidance. Only bounded canonical request-context identifiers from `ApiClientError` are projected; raw messages, stacks, payloads, credentials and idempotency keys are not rendered by this support-reference component. References are individual HTTP-attempt tracing aids, not batch identities, retry keys or proof of success. They remain in component memory and clear on new attempts, success, file reselection, scope changes and unmount; existing late-response guards suppress old-scope references. Read-only history normally has a correlation reference only. Missing or malformed context and network/local errors produce no fabricated reference. Browser regressions cover all five versioned import preview/apply channels, history retry, identifier replacement/clearing, late scope responses, keyboard use and narrow wrapping. This is bounded foundation usability, not full observability or WOS-03B acceptance.

The initial API failure-log pilot emits one structured record when an `/api` response finishes with status 400 or greater. It records timestamp, level, service, API namespace, method plus the matched route template (or a fixed `<unknown>` marker), status, a stable status-derived code, and validated correlation/operation IDs. It does not log raw paths, payloads, query values, other header values, or thrown error details. This pilot does not complete WOS-NFR-OBS-001–006; job-runner and integration logs, duration and actor context, metrics, alerts and runbooks remain open.

Production mutation code uses the shared audit writer. It records actor identity, active role, source, module/action, entity identity, before/after values, reason/details and request correlation/operation IDs when present. System operations may omit request IDs. New audit fields are nullable and added with additive migrations so historical rows are not assigned fabricated context. The existing append-only database guard remains in force.

The employee master CSV apply path also records each successfully applied row's source identifier, server-generated import batch ID and successful processing result on its audit event. The same batch ID keys the import-history result; row audits and batch history commit or roll back together. The nullable batch reference has no foreign key to the operational log so audit retention can outlive import-history retention; both records are written in one transaction.

The client master CSV apply path follows the same successful-row provenance contract. It stores the source-row `id` when supplied, leaves the audit source identifier null when that optional input field is absent, and uses one server-generated batch ID for the row audits and import-history result. The project master CSV apply path stores the required `projectCode` as its source identifier and uses the same batch linkage. The Allocation Control CSV apply path stores its optional source-row `id` when supplied, leaves that audit source identifier null when absent, and uses the same server-generated batch ID for row audits and import history. The timesheet CSV apply path preserves its existing grouping of rows into one timesheet per authorized employee/week and one audit event per persisted group. Its current input contract has no upstream row ID, so the group audit retains a null source identifier and uses the same server-generated batch ID as import history. Successful group audits record `Success`; aggregate Partial/Failed history continues to count source entries. Existing client/project/allocation/timesheet matching and upsert behavior, row errors, partial outcomes, scoped over-allocation checks, reporting-period checks and transaction boundaries remain unchanged. A concurrent project-code conflict is rechecked in the atomic upsert and rejected row-locally if it belongs to another legal entity. Allocation updates cannot use a source row ID to overwrite a record in another organization or legal entity. Raw CSV contents are not stored. For these five CSV apply paths, the existing scoped import-history error contract retains only the original row number, field, safe message and an optional validated source identifier. Preflight IDs are selected from the original parsed CSV row before invalid rows are filtered; server-generated errors attach IDs only when the valid-row-to-original-row mapping is proven, and otherwise keep the ID null. Client-supplied IDs are untrusted diagnostic provenance only, never identity or authorization input. IDs are bounded to 200 characters and reject blank values and Unicode controls/format/surrogate characters. Older clients may omit the field, and timesheets retain null because they have no upstream row ID. The separate generic `POST /api/import-export-logs` endpoint retains its legacy free-form channel label and syntactically validates optional client-supplied IDs but cannot assert upstream identity or channel-specific rules; those values remain caller-supplied diagnostics. The CSV UI numbers parsed nonblank rows, so displayed row numbers can differ from physical file lines after blank lines. Rejected-row source IDs for other import paths, schema-version/idempotency/dry-run evidence, other import/integration paths, and configurable retention remain open.

The import/export page and the existing `GET /api/import-export-logs` reader use `imports.manage`. Import-history responses remain limited to the exact server-resolved organization/legal-entity pair and the latest 100 rows. This permits authorized import users to inspect saved filenames, row-error details and caller-supplied source identifiers; it adds no broader scope or permission grant. Import/export UI requests retain their initiating organization/legal-entity pair. If the user switches scope during an apply, stale success and error details are hidden and short-lived generic import-apply/export notices survive the scope selector’s full-page reload on both the Import / Export page and Reports Center. Report exports are canceled before download if scope changes while data is loading; after download starts, history and audit writes remain explicitly bound to the captured pair. ## Compatibility and deprecation

Compatibility routes have an owner, migration plan, tests and removal release. A compatibility endpoint must not recreate a raw-source-to-batch shortcut, duplicate current line occupancy, split one approved-unbilled item, duplicate final-state export or weaken occupancy state semantics. Breaking changes require versioned contracts and release notes.

## Invoice-batch approval correction contract

The server atomically finalizes an invoice-batch approval and moves the batch to `Approved`; no pending approval may coexist with `Approved`, `Exported`, `Billed/Confirmed` or `Cancelled`. Generic reopen requests for those states, including stale or replayed requests, return a stable conflict and perform no writes. Pre-export correction is a protected cancellation command that verifies authority and version, records reason/audit, releases occupancy atomically, and creates no implicit approval; a replacement batch and approval use current eligible items. Failed export retains `Approved`. Post-export correction uses versioned reversal/supersession and a separately approved correction batch. API, persistence and role navigation expose the same state machine.
