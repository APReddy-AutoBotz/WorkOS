# Commercial candidate owner and governed approval — acceptance plan

## Lineage and selected decisions

WOS-COM-014/015, APR001–003/006, INT002/005 and CORE003–005 require auditable scoped commercial changes, configured named-stage decisions, segregated confidential costs and mandatory server-resolved recipients. APPROVAL_AND_POLICY_ENGINE_SPEC defines generic stage and notification contracts. The approved source decision is an explicit append-only owner relationship per immutable commercial candidate version, an existing active, scoped account and held role; no creator, project, engagement or title fallback. Ownership does not confer approval, administration or financial authority. Assignment and reassignment are explicit and preserve prior ownership history; a changed or ineligible owner makes decisions based on earlier owner evidence stale and requires fresh governed review. No live account or role grants are made.

The existing billing administrative boundary combines `commercial.contracts.manage`, `commercial.contracts.view`, and `commercial.rate_candidates.view/manage`; the existing confidential-cost boundary combines `commercial.cost_candidates.view/manage`, `commercial.contracts.view` and `employees.view` with current worker scope. All are pre-existing opt-in capabilities; no grant is seeded. The proposed owner's selected existing role must independently provide scoped source visibility and inbox access appropriate to the candidate kind. The worker-scoped cost owner must independently have the same worker visibility; the assignment actor also retains its own current scope. Explicit selection never changes privileges.

## Ownership phase and remaining approval dependency

The first bounded implementation exposes explicit owner assignment and reassignment for the exact candidate version, separate from rate editing. Billing assignment requires `commercial.contracts.manage` in addition to the existing billing candidate permissions; confidential cost assignment requires the existing separate cost candidate permissions and worker data scope. Selected account IDs and held roles are supplied explicitly; the endpoint does not enumerate accounts or expand a user's access. The server checks an existing active scoped account, current role, source-read permission, inbox permission and, for costs, worker visibility. Missing or ineligible owners remain unavailable. Immutable owner versions are linked to the exact candidate, and returned current eligibility is a current observation, not a permanent authorization grant. Same-key replay and exact-owner-version CAS are retained with redacted audit; original unowned candidates remain unchanged.

This phase does **not** create pending approvals or decisions, does not approve or activate rates and does not feed valuation or invoices. The configured multi-stage commercial workflow, mandatory notifications, pending-owner revalidation and fresh review on ownership or eligibility change remain the immediately subsequent dependency described above. The ownership ledger supplies a pinned version for that later workflow; it does not by itself prove any stale-decision or downstream financial behavior. Use the existing exact-head frozen acceptance and hosted receipts before crediting even this ownership phase.
