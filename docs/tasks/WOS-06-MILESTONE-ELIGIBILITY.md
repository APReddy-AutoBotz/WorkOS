# Accepted milestone billing eligibility — local development plan

WOS-COM-008, WOS-INV-001/003/005/008, WOS-APR-001/003/006, WOS-INT-002 and the Commercials Revenue Margin Specification require an accepted milestone version, required client/internal evidence and an independent configured approval before an eligibility event and exactly one approved-unbilled item exist. The original development branch started at PR110, before the independent action-notice and T&M-report siblings were composed into PR113.

## Boundary and choices

- The existing immutable milestone is source version 1, not an acceptance. The source must be a positive-value milestone-model engagement in the same organization/legal entity, with its explicit current commercial lifecycle and native currency. Contract or engagement amendments currently make the source unavailable until their exact source treatment is implemented; the implementation does not infer amended terms. There is no rate calculation, FX, earned-management recognition or invoice posting.
- An authorized manager explicitly configures a prospective named approval policy, acceptance-evidence class and evidence reference. A user-entered external/client reference is retained as an attestation, never represented as verified provider/client confirmation. Absence of the explicitly required evidence or policy fails closed. No implied buyer policy or grant is created.
- A named owner and requester are retained separately from named approval stages; self-decision, foreign scope, stale policy/source or lost current authority is refused. Pending, intermediate, rejected or invalidated states create neither an eligibility event nor register item. A final valid decision atomically creates exactly one versioned milestone event and register item with source, scope, owner, acceptance evidence, policy, decision, amount and currency lineage.
- Additive migration 088 uses an explicit source discriminator and separate milestone guard for the shared event/register boundary while preserving the existing T&M guard and existing rows. Existing T&M snapshot IDs and historical evidence are unchanged. Milestone items are visible in a scoped milestone register and can enter the separately guarded milestone invoice batch and CSV paths after the required decisions. The composed reconciliation report and action-notice sibling paths retain their documented T&M-specific scope; they do not imply milestone reconciliation or a new delivery channel.
- Preserve current held-role, account, permission and legal-entity scope checks, named staged decisions, audit and required in-app recipient effects; no automatic scheduler or external delivery. Existing required stages and recipient effects must remain atomic at commit.

## Acceptance

Use synthetic React/API/PostgreSQL journeys for explicit policy and evidence → pending/intermediate/rejected/final stages → one event and one register item. Verify independent named approvers, current source/owner/policy/role/scope and positive native amount at each decision and final commit; same-key and concurrent replay; stale and revoked authority; required notification/audit rollback; direct SQL and compatibility bypass refusal; no raw milestone directly in a batch. Prove fresh migration, existing-data upgrade and replay with unchanged T&M event/item and invoice occupancy behavior. Exercise a real role-scoped UI, a separate scoped milestone register and the source-specific invoice paths; report unsupported report and other-source paths explicitly. Use only disposable synthetic fixtures and existing local infrastructure; no production credentials, real grants or external action.
