# Pre-submission invoice action-required notice

WOS-INT-002/003/005, WOS-INV-005/006 and APPROVAL_AND_POLICY_ENGINE_SPEC require the canonical `invoice_batch.action_required` event for a genuine pre-submission invoice deficiency, addressed to the retained batch owner and finance preparer, deduplicated with reasons. It must not duplicate a generic pending-stage or rejection/correction notice. TEST_STRATEGY requires authorization, relationship scope, mandatory in-app delivery and idempotency.

Bounded first trigger: an explicitly requested pre-submission readiness assessment of a scoped Draft with current retained-owner authority whose retained line count is zero. No alert is inferred merely from creating a Draft. The existing `invoice_batch_source_current` is intentionally false for empty Drafts, so use `invoice_draft_owner_current` plus the protected batch and scope checks. The server locks the exact source and proves current Draft state, no pending generic stage, no rejection/correction operation, exact line-count/lineage and a zero-line deficiency before emitting. A nonempty, stale, cancelled, approved, exported or pending-review source is refused or produces no event. Subsequent new remediation evidence is not inferred from arbitrary text. The requester cannot provide recipients or template content in the operation. A separately configured prospective template provides approved locale and variables; no policy, recipient, grants, scheduler or external delivery is seeded.

Retain one idempotent operation and versioned source observation, sanitized event, complete required recipient-reason mappings and mandatory in-app delivery in one transaction. Resolve current explicit owner and preparer identities and roles server-side, enforce both source scope and current actor authority, deduplicate same person with both reasons and fail closed on a missing or out-of-scope recipient. Same-key replay returns the original result without a duplicate; changed payload or stale source conflicts. Preserve audit and immutable history. Current owner/recipient scope, batch state and deficiency must hold through commit. Read/acknowledge through the existing recipient-owned canonical inbox. No generic stage or rejection notice is created, no external notification is delivered and no financial authority is changed.

Acceptance must exercise real React/API/PostgreSQL explicit configuration, empty Draft assessment, exact source and owner/preparer reasons, same/different recipients, inbox/read, idempotency and concurrency; no event for nonempty/pending/rejected/exported or foreign/unauthorized cases; complete rollback on second-recipient/audit failure, user/role/scope loss, source mutation races and replay. Prove additive fresh/populated upgrade/replay without grants or historical rewrites and existing invoice approval/CSV regressions. Run targeted development checks, affected clean-checkout evidence and unchanged hosted CI. This slice supports only the explicit empty-Draft trigger; other evidence, reconciliation and export-preparation deficiencies remain open.

For application rollback, stop initiating assessments and revert the application release. Retain the additive migration and ledger rows for audit and subsequent upgrades.
