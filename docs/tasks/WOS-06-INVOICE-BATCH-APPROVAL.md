# Configured invoice-batch approval — bounded continuation plan

## Requirement lineage and dependency

WOS-INV-006/008, WOS-APR-001–003/006/008, WOS-INT-002/005 and the approval and commercial specifications require protected invoice-batch transitions, immutable evidence and database-unique occupancy. Migration 065h extends the invoice draft tables accepted in PR #190.

## Boundary

Use an explicit prospective configured policy with named current in-scope approvers and existing canonical staged-approval notification semantics. A currently authorized finance actor explicitly submits a nonempty current Draft and its retained line, item, event, source and native-currency control totals. Retain source version, owner/preparer/requester relationships, approver identity, reasons and decisions. Pending/intermediate review keeps the whole-item occupancy unchanged. A final valid decision atomically commits the terminal approval with `Under Review → Approved`, no pending stage and the same occupancy. Rejection or correction records the canonical rejection and returns the batch to a correctable `Draft` without releasing occupancy or rewriting evidence. Cancellation from permitted pre-export states requires its existing scoped protected authority, reason, audit and atomic occupancy release; any active stage must become terminal in the same transaction. Do not offer generic reopen after `Approved`, `Exported`, `Billed/Confirmed` or `Cancelled`. Changing a policy or losing and regaining authority never revives stale pending actions or rewrites past evidence.

No seeded policy, implicit role mapping, real user grants, statutory invoice, provider delivery, export or downstream billing confirmation is introduced here. Approval identity remains separate from named ownership and preparation, with self-approval excluded under the existing approval contract. For this T&M-only source contract, each distinct worker referenced by a retained work source is an affected worker for canonical rejection and completion notices. Resolve exactly one current active in-scope account for each worker; if a mandatory relationship is unavailable, fail closed. Notices contain only sanitized batch identity and stage, never monetary amounts. Resolve the complete canonical mandatory recipient set from these retained relationships plus the invoice owner and finance preparer on rejection; deduplicate identities while preserving reasons. Persist each event and every protected recipient atomically, and fail closed on missing or out-of-scope mandatory relationships. No caller-directed recipients or competing domain action event on the same decision. Optional external delivery remains out of scope.

## Acceptance before any publication

Prove real React/API/PostgreSQL configured named multi-stage review, retained whole-source inspection and exact control totals, no pending/intermediate source or occupancy mutation, single atomic final approval, rejection/correction and authorized cancellation. Exercise stale and changed-source/version refusal, owner/approver revocation and restoration, self/foreign/unauthorized decisions, direct compatibility and SQL bypass refusal, decision and cancellation races, replay and uncertain responses, and no partial recipient persistence. Verify immutable prior lines and approval evidence, no forbidden reopen, unchanged opt-in grants, additive fresh/populated upgrade/replay and session/scope fencing. Run targeted development checks, a justified independent clean-checkout affected subset on a frozen head and the unchanged full hosted CI. Delegated invoice decisions, bulk invoice decisions, due/escalation handling, export acceptance, provider delivery, later corrections, other source types, formal review, integration, UAT and release remain open. This slice does not claim full generic-approval parity.

An authorized cancellation operator inspects the batch with `forCancellation=true` and submits the returned token as `expectedCancellationToken`. A change in membership, owner validity or review progress requires a fresh inspection. Legacy commands can cancel an original unsubmitted draft and replay an existing receipt. The transaction preserves audit history and releases reservations only on successful cancellation. For rollback, suspend cancellation permissions before reverting the application and restore them after the review guard is available. Existing receipts and reservations require no data conversion.

When submitting a draft, inspect its lineage and control total and explicitly select the policy effective today in UTC. The server resolves that version independently of the recent policy list and validates it again on submission. Policy maintenance uses the latest recorded version. The optional effective-policy lookup retains the engagement authorization check. Application rollback preserves policies and batch review records.
