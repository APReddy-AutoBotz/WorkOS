## One coherent supported outcome

Explicit configuration -> new approval instance/stage -> retained pending clock -> inspected on-demand reminder -> canonical required in-app current-stage inbox/read -> existing decision or overdue flow. No automatic schedule, external delivery or new decision authority.

1. Adopt a separate append-only reminder policy linked explicitly to one existing immutable due-policy version. It uses that version's selected workers/source kinds/new-instance cohort; no inferred scope or default policy. The actor explicitly enters a positive whole-minute reminder interval strictly less than the selected due interval, locale, canonical action-required template and reason. No reminder rule is installed by migration. Later edits append a new prospective version; they never rewrite old bindings/clocks/templates/decisions or reinterpret an omitted legacy due-policy field.
2. Only approval instances created after adoption may bind the reminder policy. All later stages retain that instance binding and their original pending timestamps. Old instances/old clocks never acquire a reminder retrospectively, even when their next stage starts later. Source, due-policy and reminder-policy linkage is retained atomically through ordinary creation. Unknown/unconfigured or zero-worker policies stay inactive rather than adopting defaults.
3. A reminder is a separate authenticated on-demand triggering operation for an already valid current pending stage, using canonical `approval.action_required`, not a new domain-specific event key. It does not create another source-stage transition or reset its due clock. At most one reminder event exists for the retained clock/policy; an exact replay returns its original receipt, another request reports the existing notice. Waiting, overdue, terminal, stale and unconfigured stages emit nothing. The ready interval is inclusive reminder instant and exclusive due instant in UTC; the existing overdue contract remains unchanged.
4. Resolve the current original approver and any currently eligible bound delegate through existing server actor/source/relationship checks. Do not include an escalation target before overdue, infer a manager, accept client recipients, grant visibility, impersonate or transfer a stage. Revocation/expiry/account/permission/scope loss must affect future reminder resolution without erasing earlier accepted notification/decision evidence. Missing/invalid mandatory recipients fail visibly.
5. Commit the evaluation, exact event/template identity, complete deduplicated mandatory recipients/reasons and accepted in-app delivery in one transaction. A recipient/delivery failure rolls back all protected effects. Corrected same-key retry is exact-once. Existing source locks serialize decision/cancel/edit/reminder races; immutable current-stage/source/phase CAS prevents stale inspection. Own-recipient read acknowledgements preserve the existing server scope and actor contract. No new permission/grant or compatibility/SQL bypass is added.
6. Keep the original due-policy/configuration contract and every old migration unchanged. An additive empty migration may add only reminder policy/binding/evaluation/event/recipient/delivery/read evidence and guards. Fresh, nonempty069 upgrade and replay must preserve prior policies/clocks, roles/grants, source/work/assignment/leave/history and actual/export bytes.
