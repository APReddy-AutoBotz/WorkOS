# Governed T&M valuation — bounded development plan

The original design and evidence notes below describe the earlier draft. The current mainline integration uses migrations 065b–065f and the acceptance gates in the WorkOS CI workflow.

## Requirement lineage and dependency

WOS-COM-001–004/006/013–015, CORE003–005/008, IAM003/005/010 and the commercial specification require deterministic decimal-safe T&M calculations from approved eligible work, exact effective rate/cost/rounding sources, protected visibility and retained source evidence. Base the isolated development branch on frozen approved-rate-source candidate `48fa23911d077f77b9c2464b51768da4dc0258c6`, tree `b080f902507de14fd80bbcc3065cffd6a34b8085`. This is not integration: do not publish until that dependency itself has been published and its exact-head hosted gates pass.

## Explicit selected boundary

An authorized commercial actor explicitly configures a prospective, versioned engagement policy with currency, precision, rounding mode, per-entry rounding explicit no-cap/no-exclusion treatment and an explicit choice that no additional approval is required for this policy. A buyer requiring policy approval must leave this workflow unavailable until the canonical policy-approval path is implemented; no treatment is preselected. Supported rounding modes are decimal half-up, half-even and down; every field must be entered, with no buyer default. Unsupported caps, exclusions, FX, unit conversions, overtime pricing, amended commercial terms and other engagement models remain unavailable rather than guessed. The T&M model, selected engagement and original governed project binding must come from retained authoritative sources.

Calculate only explicitly selected, positive billable entries with retained governed T&M project/binding/assignment references and an exact approved immutable work-submission decision. Each source has an exact work date, unit HOUR and explicit native currency. Both adopted billing and separately confidential cost sources must resolve uniquely for that date, currency and unit; ambiguity, missing authority, unavailable legacy lineage or mixed currency makes the command fail closed. Pin the exact work submission/entry/approval, governing term references, adopted candidate/approval/owner versions, rounding-policy version, actor and UTC time. Use integer-decimal arithmetic, preserve exact quantities and unrounded products, then apply the explicitly selected precision/mode once per entry. Revenue, cost and margin here are operational calculation evidence only; there is no eligibility, invoice or statutory-recognition authority.

A protected append-only snapshot and line ledger, scoped by organization/legal entity and engagement, must retain immutable original evidence and results with a redacted general audit. Avoid double valuation of the same source entry by a database-unique current occupancy in the same transaction; exact retry returns the same snapshot, changed keys and competing requests conflict. Corrections/reversals and release of occupancy remain unavailable until their explicit lineage is implemented; no historical rewrite or implicit revaluation. New explicit valuation creation/read and margin permissions are opt-in definitions with no role or user grants; existing billing and cost access, scope and current named actor/role remain independently required. No real accounts or permissions are configured.

## Acceptance before publication

Prove real React/API/PostgreSQL configured policy → governed work approval → explicitly adopted billing/cost sources → T&M valuation with exact source and rounding evidence. Cover no-policy, missing/conflicting rate, wrong currency/unit, unapproved/rejected work, legacy/unbound, unauthorized/foreign/cost visibility, immutable historical references, current role/scope/source changes, same-key replay, different-key/concurrent duplicate refusal, audit rollback and session-switch/uncertain-response handling. Prove explicit rounding ties and decimal extremes without floating point, additive fresh/populated upgrade/replay with no buyer grants or backfill, and unchanged prior work/approval/rate histories. Use focused development tests and a justified independent fresh-checkout subset, then unchanged hosted CI on a dependent Draft. Full period aggregation, caps/exclusions, FX, additional financial models, billing eligibility, register/batches, formal reviews, integration, UAT and release are separate unpassed outcomes.

## Period gross margin

Select an engagement and inclusive work dates, then load the period margin. Each currency row totals the retained rounded values of entries visible under the current workforce and confidential cost permissions. Gross-margin percentage divides total margin by total billable value and rounds to two decimals, with ties away from zero. A zero denominator displays as undefined. Reload to include newly retained entries. Billing eligibility remains a separate decision. The report performs no writes and requires no migration. Reverting the application removes the report. For retained figures, use the numbered period versions below.

## Retained period versions

Load the period and choose **Retain this period** to save the inspected membership and native-currency totals. Creation requires valuation creation, cost access and visibility of all contributing workers. WorkOS records the scope, actor, calculation version, exact valuation IDs, worker IDs and audit event. Repeating the same selection returns its existing version. Later work adds a version when an authorized user inspects and retains the updated report. Open a version by number or leave the field empty for the latest. Current permissions and access to every retained worker govern historical reads. Open a retained version to page through its contributing entries and inspect the original billing and cost rate receipts.

Migration `065s_wos06_tm_period_versions` adds append-only storage without grants or backfill. Roll back the application while preserving the table and its history. Period locking, non-T&M amounts and portfolio reporting remain open.

## Financial period enforcement

New T&M valuations use the approved entry's work date. A Weekly reporting period must cover it. Every covering Weekly, Monthly and Fiscal period must permit financial work. Open, Submission Closed and Approval Closed permit valuation of work already approved. Planned, Financially Locked and Closed prevent a new snapshot. PostgreSQL coordinates each insert with organization setup, including concurrent creation of a covering period. Existing receipts, report versions and same-request replays remain available under current access controls.

Migration `065t_wos06_tm_financial_period_lock` adds an insert trigger without backfill, role grants or changes to existing amounts. Keep the database guard when reverting the application. Protected reopening and post-export corrections remain separate work.

## Protected financial reopening

In Governance, inspect a reporting date, select the frequency and review the full date range, status and revision. Locking requires settings management and a reason. Reopening also requires the explicit `periods.financial_reopen` permission. It returns Financially Locked to Approval Closed. Other covering locks still apply. Previously approved work may be valued once every covering period permits it. Work submission, approval, retained valuations, invoice batches and exported artifacts retain their existing history and rules. A stale or uncertain result requires inspecting the current revision before another action.

Migration `065u_wos06_financial_period_reopen` adds reporting-period revisions and a deferred database check for the authority and audit evidence of a financial reopen. Existing periods start at revision 1. No role or user grant is seeded. Keep the database migration and history when reverting the application.
